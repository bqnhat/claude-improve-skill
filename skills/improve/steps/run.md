# Running one upgrade

## loop: the measured upgrade loop

Show the user which station you are at as you go. `S` below stands for `node ${CLAUDE_SKILL_DIR}/scripts`.

1. **Evidence.** Restate the item's reasons. The script's corrections and tool errors are leads found by a time window after a skill ran, not proof that the skill caused them: read the transcript lines around each one (session id prefix and date are in the evidence) and write down, in one sentence each, what the user expected and what the skill did. Drop a lead the transcript does not support.
2. **What can be measured.** `claude plugin eval` loads only the target plugin; user settings, hooks, rules, `CLAUDE.md` and other plugins are absent from the run. A change inside the skill folder is measured by its suite. A hook or script is measured by tests (`node --test`) on fake data. A change to `settings.json`, a rule, or an agent outside the skill folder is not measured by any skill suite: say so before starting, and report it as unmeasured unless a case's scaffold installs the file inside the plugin.
3. **Snapshot.** Before writing any case, grader or change, snapshot every path the round may touch, the skill folder with its `evals/` included: `S/snapshot.mjs start <round> <paths...> --exclude skills/<name>/<eval dir>/results` (paths under `~/.claude`; a folder also covers files and folders added inside it later, and a path that does not exist yet is tracked from its first file). Eval output that a `record.mjs --freeze` declared (the eval folder's `results/` and its `--exclude` folders) is left out by every later `mark`, `revert` and `keep` too, even when the freeze came after `start`, so revert never deletes recorded runs; pass `--exclude` for any other output folder. The snapshot's own storage is never tracked. Do not commit, stash or stage the user's other work; `start` notes files that already held uncommitted work so `keep` can leave that work out.
4. **Case.** Turn each real failure into an eval case in `skills/<name>/evals/<case>/`, starting from `templates/case/`: a `prompt.md` close to the real request, graders, and one `tool_used` grader on `Skill`. A skill without `evals/` gets 3 to 5 cases: the failures, one plain trigger check, and one negative case where the skill must not fire (`tool_used` on `Skill` with `min: 0`, `max: 0`, `arm: both`). Also write one held-out case: a different wording of the same failure that you do not look at while changing the skill. `claude plugin eval init` may draft cases; review its graders before use.
   - Grade actions with `tool_used`, `tool_order` or `file_exists`; grade text with `regex` or `llm` on `last_message`. Never `regex` with `target: trace`: the trace holds the loaded SKILL.md body, so a pattern the skill text contains always matches. Use an `llm` grader with `focus: trace` when a claim in the reply must be backed by a tool call in the trace.
   - A slash-command prompt (`/improve ...`) loads the skill by command expansion without a Skill call, so its `tool_used` Skill grader reads 0 even when the skill ran, and no `tool_order` may require a Skill call first.
   - A case that must prove a script ran and returned the right result gets a deterministic fixture: a `case.yaml` whose `scaffold_script` writes the inputs (for a script that reads `~/.claude`, under `$HOME/.claude`), a prompt that asks to save the script's output to a file in the workspace, `file_exists` on that file and `regex` graders on `target: {source: file, path: <file>}`. A `tool_used` on Bash alone shows only that a command started. Add a `node --test` check that runs the scaffold and the script locally and matches every file grader against the real output.
   - On native Windows, Bash and PowerShell are removed from the run unless granted, and granting them makes every run fail. A case that must prove a command ran goes in `evals-wsl/` and runs under WSL2 with `--eval-dir evals-wsl --allow-tools Bash`; on Windows, grade the written command with a `regex` on the reply and keep an `llm` grader only for unbacked claims. A written command and a command that ran and returned the right output are two different results: report them apart.
5. **Baseline.** Ask for the budget. Freeze the files right before the run, run, then save the result under the same label, from the skill folder:
   ```
   S/record.mjs <skill> before-<short reason> --freeze --eval-dir <eval dir>
   claude plugin eval . --trust-plugin --no-publish --scaffold --allow-tools Read --model <full model id> --judge-model claude-haiku-5-5 --max-cost-usd <budget>
   S/record.mjs <skill> before-<short reason> --model <same id>
   ```
   The result shows the model under test as `suite.modelOverride` (set by `--model`, which overrides every case's `model:`) or, without `--model`, as each case's `model:`. record.mjs requires `--model`, refuses to save when it disagrees with the result, and adds the file hashes taken at the freeze and the test contract apart from the skill's own files; compare calls a result that shows no model `INSUFFICIENT EVIDENCE`, whatever was declared. The contract is everything under the eval folder named at the freeze (`evals` unless `--eval-dir` says otherwise, the same folder the eval command uses): each case folder with its prompt, graders, fixtures and scaffold, plus shared files such as mocks. Only that folder's `results/`, the run's own output folder and `--exclude` folders count as output; no file is left out for its name. A case outside the declared eval folder marks the result `content NOT verified`. Change nothing under the skill folder between freeze and save: a file that changed during the run is listed and the result is marked `content NOT verified`. With `--output-dir` or `--json <path>` inside the skill folder, pass `--from <run dir>` when saving and `--exclude <dir>` to both calls. Never Read `aggregate-result.json` or a trace: they hold full transcripts and flood the context. Read results only through `S/compare.mjs`.
6. **Change one thing.** For a skill or agent prompt, first invoke the `claude-api` skill with `prompt-audit` on the target file (SKILL.md or `agents/<name>.md`, plus any rule it loads). Keep only findings tied to the failure from step 1; list the rest for a later round. Skill text or description: use `/skill-creator`. A rule that must always hold: add or extend a hook. An agent problem: edit the agent file, or use `fold` below. Nothing else in the same round. Then `S/snapshot.mjs mark <round>` so the experiment's own edit is recorded.
7. **Measure again** with the identical command and the same `--model`, between `S/record.mjs <skill> after-<short reason> --freeze --eval-dir <eval dir>` and `S/record.mjs <skill> after-<short reason> --model <same id>`. A `--runs 1 --ablation none` run is fine while editing graders; confirm the result at the default 3 runs. If the cases, graders, fixtures or scaffold changed since the baseline, re-run the baseline first, because the old scores no longer compare. When scripts changed, also run `node --test` in the skill folder.
8. **Report** from `S/compare.mjs <skill> --before <before label> --after <after label> --snapshot <round>`. It uses the official per-case scores, counts errored runs in both arms, refuses unreadable or schema-breaking result files instead of falling back to an older run, and ends with one verdict:
   - `comparable` (exit 0): the only verdict that allows a keep/revert decision.
   - `INSUFFICIENT EVIDENCE` (exit 3): the model under test, CLI version, judge model (when llm graders exist), threshold or ablation, test contract or content proof (no freeze) is not recorded. Record what is missing and measure again.
   - `NOT COMPARABLE` (exit 2): fix what it lists under `blocking` (run errors, a partial run, paid graders skipped in either arm, a declared model the result contradicts, a different model, judge, CLI, threshold or ablation, a changed case definition or test contract, files changed during a run, broken result files, a change outside the evaluated plugin, a run that did not load the changed file, a snapshot started after the baseline was frozen) and measure again.

   The `fired` column counts with-skill runs whose `tool_used` Skill indicator passed; it is never part of the scores, and `*` marks slash-command prompts where 0 does not mean the skill failed to load. Report per case before, after, lift against no-skill, run errors in each arm, fired, cost and duration, the held-out case separately, and the warnings, with script tests, reply checks and model behaviour as separate lines. Three runs per case is a smoke check: say that a change of one run in three is within noise, and for a change with wide effect ask whether to spend on `--runs 5` or more cases. To see why one grader failed, open only that run's grader `explanation`, not the whole file. Ask: keep or revert.
9. **Close.**
   - Keep: `S/snapshot.mjs keep <round>` checks that no file changed after the mark and that no added line looks like a secret. It stages nothing itself: it prints `git add` for files that were clean at start and a `git apply --cached <patch>` for files that already held the user's work, so only the experiment's hunks are staged, and it lists paths that were already staged before. A file whose index already holds the user's staged changes blocks keep, because any commit of that file would carry them too; the user commits or unstages that part first. Run exactly the printed commands, then a plain `git commit` with a message stating the measured change (for example `0.67→1.00`), never a commit limited to paths or with `-a`, which takes whole working-tree files; the new cases stay as regression cases; then `S/snapshot.mjs drop <round>`.
   - Revert: `S/snapshot.mjs revert <round>`. It restores only files whose content is still the experiment's, deletes files and empty folders the experiment added, checks each restored hash and never touches the git index. A file edited by someone else after the mark is refused: show the user its path and the saved original, and never fall back to `git checkout`. Keep the new cases only if the user wants them.

Machine constraints that shape the commands:
- `scaffold_script` runs only with `--scaffold`; without it the workspace is empty and every case scores 0.
- The eval sandbox blocks Read outside the workspace; plain `--allow-tools Read` is needed for skills that read their own templates.
- Pass full model ids to both `--model` and `--judge-model`: model aliases can be remapped in `settings.json`.
- A case that loads several skills must point to folders under the target.
- `evals-wsl/` needs the `claude` CLI installed and logged in inside WSL2.

## fold

1. Write eval cases for the agent's real tasks and measure the current setup as the baseline.
2. Move the agent's prompt into a skill and its actions into tools the main loop calls; keep the agent file in place.
3. Measure again with the identical command. Remove the agent only if the folded version scores at least as well, and only after the user agrees.

## cleanup

No eval suite measures this round: never cite a skill score as evidence for it.

1. List each skill with its last use (from `/skill-doctor`) and whether it has evals. When the `skill-doctor` evidence line is not `ok`, its last use is unknown: say so and never call it unused.
2. Snapshot before any change: `S/snapshot.mjs start <round> settings.json skills/<name>...` for every skill the batch may touch.
3. Ask per skill: keep off, re-enable, or remove. Apply only the answers: remove by moving the folder to `skills/.trash/` (ignored by git, so it can be restored) and deleting its `skillOverrides` entry; re-enable by deleting the `off` entry. Then `S/snapshot.mjs mark <round>`.
4. Check: `settings.json` still parses, `claude plugin validate ~/.claude --json` reports no new error, every removed folder sits in `skills/.trash/`, and no re-enabled skill keeps an `off` entry. Report the checks and the marked files.
5. The user decides keep or revert for the batch.
6. Done when: keep runs `S/snapshot.mjs keep <round>`, one commit for the batch and `S/snapshot.mjs drop <round>`; revert runs `S/snapshot.mjs revert <round>`. A failed check is reverted unless the user fixes it in the same round.

## config

1. Show every layer that sets the value, with file and line.
2. Propose one source of truth and what the others become.
3. Where an eval can carry the change (a model through `--model`, an agent file inside the evaluated plugin), measure it like `loop`; that round needs `verdict: comparable`.
4. Anything else is unmeasured, a `settings.json`-only change included (`claude plugin eval` does not load it): say so before starting and never cite a skill score for it. Snapshot first: `S/snapshot.mjs start <round> settings.json agents/<name>.md...`. Edit only after the user agrees, then `S/snapshot.mjs mark <round>`.
5. Check: `settings.json` still parses, `claude plugin validate ~/.claude --json` reports no new error, `node --test` passes for any hook or script the change touches, and the value now resolves from the one source (show file and line).
6. The user decides keep or revert.
7. Done when: keep runs `S/snapshot.mjs keep <round>`, the commit and `S/snapshot.mjs drop <round>`; revert runs `S/snapshot.mjs revert <round>`.
